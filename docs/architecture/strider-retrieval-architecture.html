Strider Retrieval Architecture

How ingested ServiceNow, SharePoint and GitHub content becomes the per-agent indexes behind the Strider chatbot, and how a user question travels from the browser to the passages that answer it.

01 System context

Three runtime components sit in Azure. A GitHub repository, DevControlPlane, is the boundary between them: it holds the configuration the pipeline reads and the artifacts the pipeline writes, and it is the only thing the training job and the chat services have in common.

02 Components

ComponentHostingResponsibility
Strider.AI.TrainingAKS workloadReads its configuration, pulls the configured sources, and writes the JSON indexes back to the repository.
Strider.AIApp ServiceThe chatbot. Decides which agents the signed-in user may use, and assembles the prompt.
Strider.AI.ContextFinderApp ServiceLoads one agent index, scores it against the question, and returns the passages worth putting in the context window.
DevControlPlaneGitHub repositoryConfiguration in, artifacts out. The system of record for the ingested corpus.

03 Repository contents

Two files are authored by people and two are generated by the training job. Nothing else couples the build path to the query path.

FileWritten byRead byPurpose
snow_index_refactored.jsonhumansStrider.AI.TrainingWhich source data to retrieve, and where to write it.
agents_metadata.jsonhumansStrider.AIAgent configuration, filtered against the user’s permissions.
service_metadata.jsonStrider.AI.Training—Every ingested article, across all sources.
[agent_name]_index.jsonStrider.AI.TrainingStrider.AI.ContextFinderThe slice of the corpus one agent is allowed to answer from.

Dictionary shape

Both generated files use the same structure — article title as key, article content as value — so the index files are a filtered projection of service_metadata.json, not a different format.

{
  "Rotating an expired integration credential": "Raise a change in ServiceNow ...",
  "Deploy runbook: Strider.AI": "1. Confirm the index file is current ..."
}

04 Build path

Run by Strider.AI.Training in the AKS cluster. Sources and destinations are configuration, so adding a source is a repository change rather than a deployment.

  1. Load configuration. The job reads snow_index_refactored.json from DevControlPlane to learn which content to retrieve and where it belongs.
  2. Ingest and parse. Connectors pull article content from GitHub, SharePoint and ServiceNow.
  3. Normalize and write back. Each article becomes one title → content entry. The job commits service_metadata.json and every [agent_name]_index.json into the same repository.

05 Query path

Run for every question a user asks.

  1. The user opens the chatbot and picks an agent to talk to.
  2. Strider.AI reads agents_metadata.json and filters it by the user’s permissions, so the agent list only ever shows agents that user is allowed to use.
  3. Strider.AI calls ContextFinder with username, question, agent and top_n.
  4. ContextFinder loads that agent’s index — the agent parameter selects the [agent_name]_index.json file — and scores its articles against the question.
  5. The top-ranked articles come back as a title → content dictionary, which Strider.AI places in the context window before processing the user’s prompt.

06 ContextFinder contract

ParameterMeaning
usernameWho is asking — carries the permissions that scope the answer.
questionThe user’s question, in their own words.
agentWhich agent is selected; selects the [agent_name]_index.json file to search.
top_nHow many ranked articles to return.

Retrieval is lexical, by hand. Candidate articles are scored and ranked with hand-written lexical logic — no embeddings, no vector store, no external search service — and the top_n highest-scoring articles are returned as a JSON dictionary in the same title → content shape as the index itself.

07 Open questions

  • Workload kind for the training job — Deployment, Job or CronJob — and what triggers a run.
  • How the write-back happens: a direct commit to a branch, or a pull request with review.
  • Where user permissions come from: Entra ID group membership, a token claim, or a list inside agents_metadata.json.
  • Whether ContextFinder re-checks username permissions, or trusts that Strider.AI already filtered.
  • How top_n interacts with the context window budget when articles are long.
  • What decides which articles land in a given agent’s index.
  • Whether service_metadata.json has a consumer, or exists as a full-corpus snapshot.
  • Collision handling — the article title is the dictionary key, and two sources can use the same title.

08 Proposed flow: Azure AI Search

Sections 01–06 describe the system as it runs today. This section proposes replacing the index JSON files and the hand-written scorer with an Azure AI Search index. The ContextFinder contract does not change — Strider.AI still sends username, question, agent and top_n, and still receives a title → content dictionary.

What changes

ComponentTodayProposed
Strider.AI.TrainingCommits service_metadata.json and [agent]_index.json to Git.Chunks articles and pushes them to the index with mergeOrUpload; deletes articles removed at source.
Strider.AI.ContextFinderLoads the agent’s JSON file and scores it lexically in code.Sends one filtered query, merges chunks back into articles, returns top_n.
Strider.AIPermission filter and chat.Unchanged.
DevControlPlaneConfiguration and the generated corpus.Configuration only. Index files retired, or kept as an audit snapshot.

Index schema

FieldTypeWhy it exists
idEdm.String (key)Source + source id + chunk number. Replaces the title as the key, so two sources can share a title.
titleEdm.StringSearchable; becomes the key of the returned dictionary.
contentEdm.StringSearchable chunk text; becomes the value.
content_vectorCollection(Edm.Single)Only if embeddings are adopted.
agentsCollection(Edm.String)Filterable. Replaces one JSON file per agent.
allowed_groupsCollection(Edm.String)Filterable. Lets ContextFinder enforce username permissions on every query.
source, url, last_modifiedString / DateTimeOffsetFiltering, citations and freshness checks.

ContextFinder query

POST /indexes/strider-articles/docs/search
{
  "search": "<question>",
  "filter": "agents/any(a: a eq '<agent>') and allowed_groups/any(g: search.in(g, '<user groups>'))",
  "queryType": "semantic",
  "semanticConfiguration": "default",
  "select": "id, title, content",
  "top": "<top_n × chunks per article>"
}

ContextFinder groups the returned chunks by title, keeps the first top_n articles, and returns them in today’s shape.

Migration

  1. Dual write. The training job keeps committing JSON and also pushes a keyword-only (BM25) index.
  2. Shadow compare. ContextFinder queries both behind a flag; compare the top_n results on real, logged questions.
  3. Cut over. Serve from the index. Add vectors and the semantic ranker only where they measurably improve results.
  4. Retire the files. Stop committing [agent]_index.json and service_metadata.json.

What it costs

  • A paid search tier for the semantic ranker; vectors also add an Azure OpenAI embedding deployment, called at ingest and at query time.
  • Private endpoints from AKS and App Service if the corpus must stay off the public network.
  • Ranking will differ from today’s scorer — validate the cut-over as a relevance change, not an infrastructure swap.

Decision needed. Whether the workload may depend on an Azure OpenAI embedding model. Without it, keyword search plus the semantic ranker is still a clear step up from the current scorer; with it, hybrid retrieval also handles questions that share no words with the article that answers them.
