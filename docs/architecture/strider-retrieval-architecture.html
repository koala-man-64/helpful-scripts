01 System context

Three runtime components sit in Azure. A GitHub repository, DevControlPlane, is the boundary between them: it holds the configuration the pipeline reads and the artifacts the pipeline writes, and it is the only thing the training job and the chat services have in common.

02 Components

ComponentHostingResponsibility
TrainingAKS workloadReads its configuration, pulls the configured sources, and writes the JSON indexes back to the repository.
ChatbotApp ServiceThe chatbot. Decides which agents the signed-in user may use, and assembles the prompt.
ContextFinderApp ServiceLoads one agent index, scores it against the question, and returns the passages worth putting in the context window.
Azure Blob Storagecontent-storagePrimary output store for per-agent index files (always written here). Also the state store for kb_metadata.json and delta_links.json, which drive incremental sync on every run. One of the eleven content source types the training job can ingest from.

Index files are written back to Git only when the file is under approximately 90 MB; larger indexes remain in blob only.

Two files are authored by people and one is generated by the training job. Nothing else couples the build path to the query path.

Dictionary shape

The generated index file uses a flat dictionary — article title as key, article body as value.

04 Build path

Run by Training in the AKS cluster. Sources and their configuration are defined in snowindex_refactored.json, so adding a source is a repository change rather than a deployment.

  1. Load configuration. The job reads snowindex_refactored.json from the local s-training/ directory — a git clone of DevControlPlane performed by the shell wrapper (run-script.sh for AKS, actions/checkout in CI) before the Python process starts. The Python code reads local files only; there is no live connection to GitHub during a run.
  2. Ingest and parse. Connectors pull content from GitHub, SharePoint, ServiceNow, Azure Blob Storage containers, and local files in s-training/AI/ (CSV, PDF, PowerPoint, plain text, markdown). Eleven source types are supported in total.
  3. Delta-merge and write back. For each agent section, existing index entries from the prior run (read from Azure Blob Storage: kb_metadata.json and delta_links.json) are merged with the new run’s results, reconciling added, updated, and deleted entries. Per-agent index files are always written to Azure Blob Storage (content-storage/agent-indexes/). The git write-back — a git add / commit / push in the shell script, outside the Python process — runs only when the file is under approximately 90 MB; for larger agents, blob storage is the only output.

05 Query path

Run for every question a user asks.

  1. The user opens the chatbot and picks an agent to talk to.
  2. Chatbot reads agents_metadata.json and filters it by the user’s permissions, so the agent list only ever shows agents that user is allowed to use.
  3. Chatbot calls ContextFinder with username, question, agent and top_n.
  4. ContextFinder loads that agent’s index — the agent parameter selects the [agent_name]_index.json file — and scores its articles against the question.
  5. The top-ranked articles come back as a title → content dictionary, which Chatbot places in the context window before processing the user’s prompt.

06 ContextFinder contract

ParameterMeaning
usernameWho is asking — carries the permissions that scope the answer.
questionThe user’s question, in their own words.
agentWhich agent is selected; selects the [agent_name]_index.json file to search.
top_nHow many ranked articles to return.

Retrieval is lexical, by hand. Candidate articles are scored and ranked with hand-written lexical logic — no embeddings, no vector store, no external search service — and the top_n highest-scoring articles are returned as a JSON dictionary in the same title → content shape as the index itself.

07 Open questions

  • Workload kind for the training job — Deployment, Job or CronJob — and what triggers a run (schedule, manual, or config change).
  • How the git write-back targets a branch: direct commit or pull request with review. (The mechanism is a shell-script git add / commit / push; the branch policy is not confirmed.)
  • Where user permissions come from: Entra ID group membership, a token claim, or a list inside agents_metadata.json.
  • Whether ContextFinder re-checks username permissions, or trusts that Chatbot already filtered.
  • How top_n interacts with the context window budget when articles are long.
  • The exact matching logic and tier hierarchy in snowindex_refactored.json — the file defines agents and user tiers, but the precedence rules when a user matches multiple tiers are not confirmed.
  • How Azure Blob Storage is accessed from AKS: managed identity, workload identity, or connection string.
  • Collision handling — the article title is the dictionary key, and two sources can use the same title.

08 Proposed flow: Azure AI Search

Sections 01–06 describe the system as it runs today. This section proposes replacing the index JSON files and the hand-written scorer with an Azure AI Search index. The ContextFinder contract does not change — Chatbot still sends username, question, agent and top_n, and still receives a title → content dictionary.

What changes

ComponentTodayProposed
TrainingWrites [agent]_index.json to Azure Blob Storage (always) and conditionally to Git (files under ~90 MB).Chunks articles and pushes them to the search index with mergeOrUpload; deletes articles removed at source.
ContextFinderLoads the agent’s JSON file and scores it lexically in code.Sends one filtered query, merges chunks back into articles, returns top_n.
ChatbotPermission filter and chat.Unchanged.
DevControlPlaneConfiguration and the generated corpus.Configuration only. Index files retired, or kept as an audit snapshot.

Index schema

FieldTypeWhy it exists
idEdm.String (key)Source + source id + chunk number. Replaces the title as the key, so two sources can share a title.
titleEdm.StringSearchable; becomes the key of the returned dictionary.
contentEdm.StringSearchable chunk text; becomes the value.
content_vectorCollection(Edm.Single)Only if embeddings are adopted.
agentsCollection(Edm.String)Filterable. Replaces one JSON file per agent.
allowed_groupsCollection(Edm.String)Filterable. Lets ContextFinder enforce username permissions on every query.
source, url, last_modifiedString / DateTimeOffsetFiltering, citations and freshness checks.

ContextFinder query

POST /indexes/articles/docs/search
{
  "search": "<question>",
  "filter": "agents/any(a: a eq '<agent>') and allowed_groups/any(g: search.in(g, '<user groups>'))",
  "queryType": "semantic",
  "semanticConfiguration": "default",
  "select": "id, title, content",
  "top": "<top_n × chunks per article>"
}

ContextFinder groups the returned chunks by title, keeps the first top_n articles, and returns them in today’s shape.

Migration

  1. Dual write. The training job keeps committing JSON and also pushes a keyword-only (BM25) index.
  2. Shadow compare. ContextFinder queries both behind a flag; compare the top_n results on real, logged questions.
  3. Cut over. Serve from the index. Add vectors and the semantic ranker only where they measurably improve results.
  4. Retire the files. Stop committing [agent]_index.json to Git.

What it costs

  • A paid search tier for the semantic ranker; vectors also add an Azure OpenAI embedding deployment, called at ingest and at query time.
  • Private endpoints from AKS and App Service if the corpus must stay off the public network.
  • Ranking will differ from today’s scorer — validate the cut-over as a relevance change, not an infrastructure swap.

Decision needed. Whether the workload may depend on an Azure OpenAI embedding model. Without it, keyword search plus the semantic ranker is still a clear step up from the current scorer; with it, hybrid retrieval also handles questions that share no words with the article that answers them.
