Investigation outline & execution plan

LaunchDarkly & Terraform
Credential Consumer Investigation

Build an evidence-backed map from each credential to its identity, configured consumers, observed activity, and responsible teams.

Prepared September 13, 2026 · Read-only investigation · Planning document

Core distinction: Where a key exists, where it is actively used, and who performed an action are separate findings. This plan covers the LaunchDarkly SDK credential and Terraform API token scripts. It authorizes neither credential rotation nor production changes.

1. Objectives and investigation questions

For each credential, determine:

  1. Which provider account, organization, project, environment, or principal owns it?
  2. Can we identify the exact credential record?
  3. Which applications, pipelines, agents, integrations, or developer environments contain or reference it?
  4. Which of those consumers show evidence of recent use?
  5. Which teams maintain those consumers?
  6. What activity can be attributed to the credential, versus merely its associated account?
  7. What remains unknown because of missing access, retention, or telemetry?
  8. What dependencies must be considered before rotation?

A shared credential cannot, by itself, establish which person used it. Credential creation, account ownership, and actual use are separate findings.

2. Scope and operating controls

Before collection, record:

InputRequired detail
Investigation referenceIncident or task identifier
Provider scopeLaunchDarkly organization/region; HCP Terraform or Terraform Enterprise hostname
Credential inputExisting approved secure input mechanism
Search scopeExplicit repositories, subscriptions/accounts, clusters, secret stores, and CI/CD projects
Time windowStart/end in UTC, including any suspected exposure period
Collection accessRead-only permissions and known restrictions
Evidence destinationApproved restricted location and retention requirements
ContactsProvider administrator and likely application/platform owners

Maintain these controls throughout:

  • Never put credential values in command arguments, search-service queries, reports, tickets, or logs.
  • Compare values locally in memory where authorized; return only sanitized locations and identifiers.
  • Treat secret-store value retrieval as a separately scoped capability; use references and metadata first.
  • Make no deployments, SDK initialization, test Terraform runs, credential changes, or permission changes.
  • Record investigation request times because diagnostic authentication may itself produce activity or change usage metadata.
  • Preserve partial findings when supplemental access fails.

3. Evidence classifications

Use explicit classifications rather than a single confidence score.

ClassificationMeaning
Identity confirmedProvider evidence identifies a principal or resource; state whether the exact credential is established.
Stored copy confirmedAn authorized local comparison found the exact value in a location.
Configured consumer confirmedEffective application or pipeline configuration resolves to the credential or a verified secret version.
Observed credential useTelemetry explicitly identifies the exact credential in an authentication or request.
Correlated activityActivity matches an application, actor, environment, or time window, but lacks an exact credential link.
Candidate consumerA plausible reference exists but its resolution or current deployment is unverified.
Unknown/incompleteAvailable evidence cannot answer the question.
A stored copy is not proof of deployment. Deployment configuration is not proof of execution. Activity by a token owner is not proof of use of that particular token.

4. Investigation phases

Phase A — Establish credential identity

LaunchDarkly

  • Run the existing identity discovery.
  • Where management access permits, identify the exact SDK credential record.
  • Capture organization, project, environment, credential resource key, available lifecycle metadata, and creator.
  • Keep creator identity separate from current operational ownership.
  • Preserve all matches and access limitations.

Terraform

  • Establish the approved HCP Terraform or Terraform Enterprise origin.
  • Identify the authenticated principal and token type.
  • Validate whether provider metadata establishes the exact token record.
  • Record accessible organizational context without equating access with ownership.
  • Retrieve supported token metadata only through documented, authorized endpoints.

Output: A sanitized credential identity record and explicit statement of what is—and is not—proven.

Phase B — Discover stored copies and configuration references

Search only the approved scope, beginning with current configuration.

Repositories and infrastructure definitions

  • Find SDK initialization and Terraform authentication configuration.
  • Inspect environment-variable names, secret references, deployment templates, and pipeline definitions.
  • Trace references through reusable templates and shared configuration.
  • Search repository history only when exposure timing or an unresolved consumer requires it.

CI/CD

  • Identify pipelines referencing relevant variable groups, secrets, credentials, or secure files.
  • Trace shared configuration to individual pipeline consumers.
  • Record recent execution and the deployed destination when available.
  • Treat masked or non-retrievable values as unresolved unless another authoritative link establishes identity.

Runtime and secret stores

  • Inspect application settings, workload specifications, mounted secret references, and agent configuration.
  • Resolve reference chains, including secret versions where available.
  • Distinguish desired configuration from the revision currently running.
  • Capture application, environment, deployment, and owner identifiers.

Developer environments

  • Include only explicitly authorized machines or supplied artifacts.
  • Inspect credential configuration through secret-safe matching.
  • Do not infer that the machine owner personally performed every authenticated action.

Output: A consumer/reference graph. Mark unresolved links individually.

Credential record
  → secret location and version
  → configuration reference
  → application / pipeline / agent
  → deployed instance or execution
  → responsible team

Phase C — Collect activity evidence

LaunchDarkly

  • Inspect application metadata and Service Connections usage for the matched environment.
  • Correlate application identifiers with the configuration inventory.
  • Check whether Relay Proxy changes visibility into downstream applications.
  • Use available application and proxy logs to corroborate connection activity.
  • Keep management audit events separate from SDK consumption.

LaunchDarkly documents application attribution through configured applicationId; missing identifiers appear as “Unknown.” Application attribution alone does not establish the exact SDK key. Service Connections documentation

Terraform

  • For HCP Terraform, collect relevant audit events using separately authorized organization or audit-trail access.
  • Correlate actor, request, run, workspace, and timestamps with CI/CD records.
  • For Terraform Enterprise, establish the installation’s supported logging route and available schema before designing collection.
  • Use exact-token attribution only if the collected evidence explicitly supports it.

HCP Terraform’s documented standard audit fields identify actors and resources, not the authenticating token. Its audit API has 14-day retention and is unavailable for Terraform Enterprise, so collect available history early. Audit Trails API documentation

Supporting telemetry

Where authorized and already available, inspect secret-access logs, workload identity records, and network/application logs. A secret retrieval proves retrieval, while an outbound connection proves communication; neither alone proves successful use of the target credential.

Output: A timeline with evidence classifications and collection coverage.

Phase D — Resolve ownership and contradictions

For every confirmed or candidate consumer:

  • Identify the maintaining team using repository ownership, deployment metadata, or service inventory.
  • Distinguish credential creator, provider principal, deployment identity, application owner, and human operator.
  • Investigate conflicting evidence, such as old repository references versus newer deployed configuration.
  • Prepare owner questions for unresolved links; send them only with explicit authorization.
  • Report dormant and historical consumers separately from current ones.

Output: An ownership map and a short unresolved-questions register.

Phase E — Prepare the investigation report

Include:

  1. Credential identity and exact-match status.
  2. Confirmed configured consumers.
  3. Observed credential use and separately labeled correlated activity.
  4. Historical, dormant, and candidate consumers.
  5. Responsible teams and ownership evidence.
  6. Activity timeline.
  7. Search coverage, permission failures, and retention gaps.
  8. Rotation dependency order and verification steps, if rotation is subsequently authorized.

Use “no evidence found within the investigated scope and period”, never “unused,” when evidence is absent.

5. Script expansion plan

Keep consumer investigation opt-in so the existing identity workflow remains useful without broad infrastructure access.

ComponentResponsibility
Existing identity collectorsEstablish provider and credential identity
Scoped configuration collectorsDiscover locations and resolve references
Provider activity collectorsRetrieve supported audit or usage evidence
Correlation layerJoin evidence using explicit identifiers and timestamps
Report writerProduce sanitized structured data and a readable summary

Each finding should include:

  • Provider and non-secret credential identifier.
  • Consumer type, name, environment, and configuration revision.
  • Reference chain and evidence classification.
  • Observation timestamp and covered time window.
  • Source locator or event/request ID.
  • Responsible team and ownership source.
  • Limitations and collection errors.

Start with one infrastructure collector selected from the actual hosting environment. Add other integrations only when the investigation needs them. Do not introduce a database or a generic plugin framework initially.

Before implementation, verify documented API availability, permissions, pagination, and response fields for every proposed collector. The LaunchDarkly usage UI’s capabilities must not be assumed to have an equivalent public API.

6. Validation and release gates

Use offline fixtures to test:

  • Exact matching without secret disclosure.
  • Shared credentials across multiple consumers.
  • Unresolved and versioned secret references.
  • Stale configuration versus running deployment.
  • Activity by the same principal using different credentials.
  • Missing application identifiers and proxy aggregation.
  • Pagination, throttling, denied access, expired history, and partial results.
  • Redirect/origin restrictions and sanitized errors.
  • Investigation-generated activity being identified separately.

Before release:

  1. Run existing script regression suites.
  2. Run new collector and correlation tests.
  3. Obtain independent security/data-integrity review.
  4. Perform a bounded, authorized read-only pilot.
  5. Verify the report against known configuration and activity.
  6. Document permissions, interpretation, limitations, and handoff procedures.

7. Completion criteria and execution order

The investigation is complete when every in-scope location has either been checked or recorded as inaccessible, every finding has supporting evidence, and remaining uncertainty is explicit.

Recommended order:

  1. Confirm scope and secure access.
  2. Establish credential identity.
  3. Preserve short-retention activity evidence.
  4. Trace configuration references to consumers.
  5. Correlate activity and resolve ownership.
  6. Produce findings and rotation dependencies.
  7. Implement only the collectors justified by the evidence gaps.
This document is an investigation plan, not a report of completed collection. No credential investigations, script changes, or runtime configuration changes are represented as completed. Runtime-ownership-enforcer: not applicable to this document preparation; ownership verification is included in the proposed investigation.
