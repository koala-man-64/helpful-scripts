01 System context

Three runtime components sit in Azure. A GitHub repository, DevControlPlane, is the boundary between them: it holds the configuration the pipeline reads and the artifacts the pipeline writes, and it is the only thing the training job and the chat services have in common.

Two files are authored by people and one is generated by the training job. Nothing else couples the build path to the query path.

04 Build path

Run by Training in the AKS cluster. Sources and their configuration are defined in snowindex_refactored.json, so adding a source is a repository change rather than a deployment.

  1. Load configuration. The job reads snowindex_refactored.json from the local s-training/ directory — a Git clone of DevControlPlane performed by the shell wrapper (run-script.sh for AKS, actions/checkout in CI) before the Python process starts. The Python code reads local files only; there is no live connection to GitHub during a run.
  2. Ingest and parse. Connectors pull content from GitHub, SharePoint, ServiceNow, Azure Blob Storage containers, and local files in s-training/AI/ (CSV, PDF, PowerPoint, plain text, markdown). Eleven source types are supported in total.
  3. Delta-merge and write back. For each agent section, existing index entries from the prior run (read from Azure Blob Storage: kb_metadata.json and delta_links.json) are merged with the new run’s results, reconciling added, updated, and deleted entries. Per-agent index files are always written to Azure Blob Storage (content-storage/agent-indexes/). The Git write-back — a git add / commit / push in the shell script, outside the Python process — runs only when the file is under about 90 MB; for larger agents, Azure Blob Storage is the only output.

05 Query path

Run for every question a user asks.

  1. The user opens the chatbot and picks an agent to talk to.
  2. Chatbot reads agents_metadata.json and filters it by the user’s permissions, so the agent list only ever shows agents that user is allowed to use.
  3. Chatbot calls ContextFinder with username, question, agent and top_n.
  4. ContextFinder loads that agent’s index — the agent parameter selects the [agent_name]_index.json file — and scores its articles against the question.
  5. The top-ranked articles come back as a title → content dictionary, which Chatbot places in the context window before processing the user’s prompt.

06 ContextFinder contract

ParameterMeaning
usernameWho is asking — carries the permissions that scope the answer.
questionThe user’s question, in their own words.
agentWhich agent is selected; selects the [agent_name]_index.json file to search.
top_nHow many ranked articles to return.

Retrieval is lexical, by hand. Candidate articles are scored and ranked with hand-written lexical logic — no embeddings, no vector store, no external search service — and the top_n highest-scoring articles are returned as a JSON dictionary in the same title → content shape as the index itself.

07 Open questions

  • Workload kind for the training job — Deployment, Job or CronJob — and what triggers a run (schedule, manual, or config change).
  • How the Git write-back targets a branch: direct commit or pull request with review. (The mechanism is a shell-script git add / commit / push; the branch policy is not confirmed.)
  • Where user permissions come from: Entra ID group membership, a token claim, or a list inside agents_metadata.json.
  • Whether ContextFinder re-checks username permissions, or trusts that Chatbot already filtered.
  • How top_n interacts with the context window budget when articles are long.
  • The exact matching logic and tier hierarchy in snowindex_refactored.json — the file defines agents and user tiers, but the precedence rules when a user matches multiple tiers are not confirmed.
  • How Azure Blob Storage is accessed from AKS: managed identity, workload identity, or connection string.
  • Collision handling — the article title is the dictionary key, and two sources can use the same title.

08 Proposed flow: Azure AI Search

§01–§06 describe the system as it runs today. This section proposes replacing the index JSON files and the hand-written scorer with an Azure AI Search index. The ContextFinder contract does not change — Chatbot still sends username, question, agent and top_n, and still receives a title → content dictionary.

What changes

ComponentTodayProposed
TrainingWrites [agent_name]_index.json to Azure Blob Storage (always) and conditionally to Git (files under about 90 MB).Chunks articles and pushes them to the search index with mergeOrUpload; deletes articles removed at source.
ContextFinderLoads the agent’s JSON file and scores it lexically in code.Sends one filtered query, merges chunks back into articles, returns top_n.
ChatbotPermission filter and chat.Unchanged.
DevControlPlaneConfiguration and the generated corpus.Configuration only. Index files retired, or kept as an audit snapshot.

Index schema

FieldTypeWhy it exists
idEdm.String (key)Source + source id + chunk number. Replaces the title as the key, so two sources can share a title.
titleEdm.StringSearchable; becomes the key of the returned dictionary.
contentEdm.StringSearchable chunk text; becomes the value.
article_idEdm.StringFilterable. Source + source id, shared by every chunk of one article, so chunks can be grouped at query time and replaced or deleted per article (§09).
content_vectorCollection(Edm.Single)Only if embeddings are adopted. Not stored or retrievable — it is only searched — which keeps index size down.
agentsCollection(Edm.String)Filterable. Replaces one JSON file per agent.
allowed_groupsCollection(Edm.String)Filterable. Lets ContextFinder enforce username permissions on every query.
source, url, last_modifiedString / DateTimeOffsetFiltering, citations and freshness checks.

ContextFinder query

POST /indexes/articles/docs/search
{
  "search": "<question>",
  "filter": "agents/any(a: a eq '<agent>')
             and allowed_groups/any(g: search.in(g, '<user groups>'))",
  "queryType": "semantic",
  "semanticConfiguration": "default",
  "select": "id, title, content",
  "top": "<top_n × chunks per article>"
}

ContextFinder groups the returned chunks by title, keeps the first top_n articles, and returns them in today’s shape.

Migration

  1. Dual write. The training job keeps committing JSON and also pushes a keyword-only (BM25) index.
  2. Shadow compare. ContextFinder queries both behind a flag; compare the top_n results on real, logged questions.
  3. Cut over. Serve from the index. Add vectors and the semantic ranker only where they measurably improve results.
  4. Retire the files. Stop committing [agent_name]_index.json to Git.

What it costs

  • A paid search tier for the semantic ranker; vectors also add an Azure OpenAI embedding deployment in the Foundry project, called by Training at ingest and by the search service at query time.
  • Private endpoints from AKS and App Service if the corpus must stay off the public network.
  • Ranking will differ from today’s scorer — validate the cut-over as a relevance change, not an infrastructure swap.

Decision needed. Whether the workload may depend on an Azure OpenAI embedding model. Without it, keyword search plus the semantic ranker is still a clear step up from the current scorer; with it, hybrid retrieval also handles questions that share no words with the article that answers them.

09 Proposed workflow, step by step

What happens, and when, once the §08 proposal is built. There are three phases, and they share only the search index and the embedding deployment: deploy runs once per index version, ingest runs inside every Training run, and query runs for every question. Steps tagged vectors apply only if S8 approves embeddings; without them the same flow runs keyword-only and those steps are skipped.

Deploy — once per index version

  1. Grant identities. Infrastructure code enables role-based access on the search service and turns on its system-assigned managed identity, then assigns the roles in the table below. Role assignments can take several minutes to take effect; nothing further works until they do.
  2. Deploy the embedding model.vectors The Foundry project has a text-embedding-3-large (3072 dimensions) or text-embedding-3-small (1536) deployment with enough tokens-per-minute quota for a full backfill.
  3. Create the index. The S2 script creates articles-v1 from the §08 schema. With vectors, the definition also carries the vector field, an HNSW profile and a vectorizer that points at the Foundry deployment, so the search service can embed query text itself. The search service has no model of its own; the model is named only in the index definition. The index starts empty.
  4. Backfill. One full Training run pushes every article — the ingest phase below, applied to the whole corpus.

Ingest — every Training run, per article

Runs after the §04 delta-merge, in place of writing [agent_name]_index.json once cut over (alongside it during dual write).

StepWhat happensResult
1. Delta-mergeThe existing §04 step, unchanged: reconciles added, updated and deleted articles against kb_metadata.json and delta_links.json.Articles to push and articles to delete.
2. Hash checkHash the article content, its agents and allowed_groups, the chunk settings and the embedding deployment; compare with the hash recorded at the article’s last successful push.Match: stop — no embedding or index cost. Otherwise continue.
3. ChunkSplit on the article’s own structure first (headings, paragraphs, table rows), then cap by tokens — about 800 with 100 overlap.Chunk texts.
4. EmbedvectorsCall the Foundry embedding deployment in batches of up to 64 chunks, retrying on HTTP 429 and honoring retry-after.One vector per chunk.
5. UpsertmergeOrUpload in batches of about 100. Chunk ids are <hash of article_id>-<n>, because keys allow only letters, digits, _ - =. Any failed chunk fails the article.Chunks written; searchable within about a second.
6. Delete stale chunksQuery chunk ids by article_id and delete those not in the new set.Leftovers from a longer previous version are gone.
7. Record the hashOnly after steps 5 and 6 succeed, record the hash in the run state kept with kb_metadata.json.The next run skips the article unless something in the hash changed.

Upserting before deleting means an edited article is never missing from search mid-update, and deterministic ids make any step safe to repeat.

What happens in each situation

SituationWhat runsIndex afterwards
New articleSteps 2–7; step 6 finds nothing.Chunks added.
Unchanged articleStops at step 2.Untouched, at no cost.
Edited, same or more chunksSteps 2–7; existing ids are overwritten.Replaced in place; never missing from search.
Edited, fewer chunksSteps 2–7; step 6 removes the extras.Only current chunks. Old extras can still match for about a second.
Deleted at sourceDelta-merge reports it; step 6 runs with nothing kept.All its chunks removed. The delta-merge is the only deletion signal — a push index never discovers deletions itself.

Run crashes after step 5, before step 7The next run repeats the article.Same result; costs one extra embedding pass.
Upload partially failsThe article fails; steps 6 and 7 are skipped.Retried next run. Articles that keep failing are reported rather than retried forever.
Two Training runs overlapEach run’s step 6 can delete the other’s new chunks.Chunks missing until the next run. Allow one run at a time — for example concurrencyPolicy: Forbid if the workload is a CronJob (§07).

Query — every question

  1. Chatbot filters agents and calls ContextFinder with username, question, agent and top_n — unchanged from today.
  2. ContextFinder resolves the user’s groups from username (S3).
  3. One search request carries the question as keyword text and also as a text vector queryvectors, which the search service embeds through the vectorizer with its own identity. The agent and group filter applies to both halves.
  4. The search service ranks. Keyword and vector results are fused (Reciprocal Rank Fusion), then the semantic ranker reorders them.
  5. ContextFinder shapes the answer. It groups chunks by article_id, keeps the first top_n articles and returns today’s title → content dictionary. It logs the question, the returned article ids and the index name for S7.
"vectorQueries": [
  { "kind": "text", "text": "<question>", "fields": "content_vector", "k": 50 }

Added to the §08 query when vectors are enabled. A question can match an article about a second after its upsert, so the lag from source to answer is set by the Training schedule, not by the search service.

If Foundry is on a private network, the search service also needs a shared private link to it; without one, indexing works but vector queries fail.

Changing the embedding model or chunk settings

  1. Create articles-v2 with the new model and dimensions.
  2. Write to both indexes. Training keeps a separate hash per index; because the hash includes the deployment and chunk settings, every article is pushed to v2 while v1 keeps receiving updates. ContextFinder still queries v1.
  3. Re-run the S7 question set against v2.
  4. Switch ContextFinder to v2 — its index name and vectorizer change together.
  5. Delete v1 once the rollback window has passed.

Never mix embedding models in one index. Mismatched dimensions fail on upload; a different model with the same dimensions fails silently, as poor ranking. Adopting vectors for the first time (S8) is the same in miniature: add the field and vectorizer, and the changed hash makes the next run re-push every article. Changing the chat model touches none of this.

ingest step sketch (Python) 
import hashlib
import tiktoken
from azure.identity import DefaultAzureCredential, get_bearer_token_provider
from azure.search.documents import SearchClient
from openai import OpenAI

ENC = tiktoken.get_encoding("cl100k_base")          # tokenizer of text-embedding-3-*
CHUNK_TOKENS, OVERLAP, EMBED_BATCH, UPLOAD_BATCH = 800, 100, 64, 100

cred = DefaultAzureCredential()                      # Training's workload identity
aoai = OpenAI(
    base_url="https://<foundry-resource>.openai.azure.com/openai/v1/",
    api_key=get_bearer_token_provider(cred, "https://cognitiveservices.azure.com/.default"),
    max_retries=6,                                   # backs off on 429, honors retry-after
)
search = SearchClient("https://<search>.search.windows.net", "articles-v1", cred)


def chunk(text: str) -> list[str]:
    tokens = ENC.encode(text)                        # split on structure before this
    if not tokens:
        return []
    step = CHUNK_TOKENS - OVERLAP
    return [ENC.decode(tokens[i:i + CHUNK_TOKENS])
            for i in range(0, max(len(tokens) - OVERLAP, 1), step)]


def embed(texts: list[str]) -> list[list[float]]:
    vectors = []
    for i in range(0, len(texts), EMBED_BATCH):
        resp = aoai.embeddings.create(model="text-embedding-3-large", input=texts[i:i + EMBED_BATCH])
        vectors.extend(d.embedding for d in sorted(resp.data, key=lambda d: d.index))
    return vectors


def push_article(article) -> None:
    key = hashlib.sha256(article.article_id.encode()).hexdigest()
    chunks = chunk(article.content)
    docs = [
        {"id": f"{key}-{n}", "article_id": article.article_id, "title": article.title,
         "content": text, "content_vector": vector, "agents": article.agents,
         "allowed_groups": article.allowed_groups, "source": article.source,
         "url": article.url, "last_modified": article.last_modified}
        for n, (text, vector) in enumerate(zip(chunks, embed(chunks), strict=True))
    ]
    for i in range(0, len(docs), UPLOAD_BATCH):
        failed = [r.key for r in search.merge_or_upload_documents(docs[i:i + UPLOAD_BATCH]) if not r.succeeded]
        if failed:
            raise RuntimeError(f"{article.article_id}: {len(failed)} chunks failed to upload")
    delete_chunks(article.article_id, keep={d["id"] for d in docs})


def delete_chunks(article_id: str, keep: set[str]) -> None:
    safe_id = article_id.replace("'", "''")          # OData string escaping
    existing = search.search(search_text="*", filter=f"article_id eq '{safe_id}'", select=["id"])
    stale = [{"id": r["id"]} for r in existing if r["id"] not in keep]
    if stale:
        search.delete_documents(stale)

A sketch, not run. Check class and parameter names against the pinned azure-search-documents and openai versions. tiktoken is there only for token-accurate chunks, since embedding limits are counted in tokens. Without vectors, drop embed and content_vector.

10 Feature and stories

The §08 proposal is delivered as one feature. Its stories follow the migration phases, and each has a testable done when check. These are proposed backlog labels, not Azure Boards IDs; publishing this document does not create work items.

Feature — Azure AI Search retrieval for ContextFinder. ContextFinder serves every agent’s top_n articles from an Azure AI Search index, with the ContextFinder contract unchanged, permissions enforced on every query, and the per-agent JSON index files retired.
